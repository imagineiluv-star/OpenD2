# 개인별 퀘스트 수락·진행 설계 제안 (M5-01d-3)

**상태: 구현됨(M5-01d-3).** 아래 1–6절은 제안 당시의 분석을 그대로 보존한다. 실제 구현과 달라진 점, 질문에 대해 가정한 답은 맨 아래 "구현 기록"에 있다. 이 문서의 현재 동작 서술은 구현 전 코드(`GameWorld.cs`, `GameSimulation.cs`, `GameRestore.cs`, `Realm.cs`)에서 확인한 것이다.

## 1. 지금의 구조

| 층 | 현재 동작 |
| --- | --- |
| Core 상태 | 퀘스트는 `GameSimulation.QuestState`(`Available → Active → ReadyToTurnIn → Completed`) **하나**다. 처치 진행(`Quest.Defeated/Required`)은 퀘스트 대상 몬스터의 생존 여부에서 계산하는 파생값이다 |
| 전이 | `Interact`가 플레이어 ID 순으로 NPC 대화를 처리하고, **tick당 한 번만** 단계가 바뀐다(`questChanged`). 처치가 끝나면 `UpdateQuest`가 `ReadyToTurnIn`으로 올린다. 완료 보상은 살아 있는 참가자 전원의 체력 회복 |
| 상태 해시 | 월드가 있으면 `world.ContentHash`, `WorldPlayer`, `ActiveRegion`, `(int)QuestState`가 해시에 들어간다. `RulesVersion = 8` |
| 콘텐츠 해시 | `CooperativeWorld.Content = ("cooperative-demo-v1", Create(4).ComputeStateHash())`. 즉 **Core 해시 직렬화가 바뀌면 콘텐츠 해시도 바뀐다** |
| 저장 | 오프라인 `GameSave`(schema 5 / rules 8)와 서버 방 저장(`SavedGame.Quest`)이 모두 `QuestState` 하나를 저장한다. 이전 규칙은 `RestoreLegacy`/`RestoreCompatible`이 메모리에서 변환한다(현재 7 → 8) |
| 서버 | `Member.QuestCredit`(#81)은 퀘스트가 `Completed`가 되는 tick 끝에 살아 있던 참가자에게 붙고, 방 종료 때 `Character.Quests`가 늘어난다. 개인별 단계는 **저장하지 않는다** |
| 와이어 | v5 프레임의 `RoomView.World.Quest`는 `QuestProgress(Stage, Defeated, Required)` 하나이며 수신자마다 따로 만들지 않는다(전원 같은 값) |
| 클라이언트 | Godot HUD가 공유 퀘스트 한 줄을 그린다 |

그래서 한 명이 NPC에게 말을 걸어 수락하면 **방 전체가 수락한 것**이 되고, 다른 참가자는 수락하지 않았어도 완료 크레딧을 받을 수 있다
(살아만 있으면). #81의 크레딧은 이 한계를 서버에서 가능한 만큼 줄인 임시 규칙이다.

## 2. 선택지

| | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. Core 개인 단계 (권장)** | 월드의 플레이어마다 `QuestStage`를 둔다(`worldPlayers`와 같은 순서). 처치 진행은 공유, **수락·완료·보상은 개인** | 규칙이 Core에 있어 서버·오프라인·재생이 같은 결과. "LLM/서버가 아니라 Core가 판정한다"는 원칙 유지 | `RulesVersion` 9, 상태 해시·콘텐츠 해시·저장 형식 변경, 기존 방/저장의 변환 필요 |
| B. 서버 겹쳐쓰기 | Core는 공유 단계 유지, 서버가 멤버별 단계를 따로 추적하고 `Interact` 명령을 가로챔 | Core 해시 불변 | 규칙이 두 곳에 갈라지고 재생·오프라인에서 달라진다. 비권장 |
| C. 서버가 이벤트만 관찰 | Core의 `NpcTalked`(행위자, 이후 단계)를 서버가 보고 `QuestAccepted`/`TurnedIn` 플래그를 저장, 크레딧 조건에 반영 | Core 불변, 작음 | 진짜 개인 진행이 아니다. 단계가 여전히 공유라 "수락 안 한 사람이 완료 NPC를 못 만난다"를 표현할 수 없다 |

권장: **A**를 단계로 나눠 구현한다. C는 A 전에 임시로 크레딧 조건만 좁히고 싶을 때의 가벼운 대안이다.

## 3. 권장안 A의 규칙 초안

- 개인 단계 배열 `QuestStage[] playerQuest`(플레이어 수 ≤ 4). `Available → Active → ReadyToTurnIn → Completed`는 **자기 단계**다.
- **처치 진행은 공유**: 몬스터 처치는 방 전체의 사실이다. 한 명이 `Active`이고 대상이 다 죽어 있으면 그 사람은 곧바로 `ReadyToTurnIn`이 된다
  (현재 `Available` 수락 시의 즉시 `ReadyToTurnIn` 규칙과 같음).
- **수락·완료는 본인이 NPC와 상호작용해야 한다.** `questChanged`의 tick당 한 번 제한은 **플레이어별**로 바꾼다(한 tick에 서로 다른 두 사람이 각자 수락 가능).
- **보상은 본인 한 번**: 완료 시 자기 체력만 회복하고, 크레딧(`Character.Quests`)은 **본인이 완료했는지**로 정한다. 죽은 사람은 NPC와 상호작용할 수 없으므로
  자연히 제외된다. #81의 "완료 tick 끝에 살아 있던 참가자" 규칙과 서버 `Member.QuestCredit` 추정이 필요 없어진다.
- 지역 이동, 사망(부활 없음), 재생, 저장 복원의 기존 계약은 그대로 지킨다.

## 4. 호환성과 마이그레이션 (A 기준)

1. **규칙 버전 9**. `ComputeStateHash(version)`은 9에서만 개인 단계 배열을 쓰고, 8 이하는 지금 직렬화를 유지한다(독립 Python 직렬화 검사 포함, `check-state-vectors.py`).
2. **8 → 9 변환**: 공유 `QuestState`를 **모든 플레이어의 개인 단계로 복제**한다. 이 변환은 정보를 잃지 않는다(공유 상태는 개인 단계가 전원 같은 특수한 경우).
   `RestoreLegacy` 목록을 `(4 5 6 7 8)`로 넓히고 변환 후 해시를 다시 계산해 검증한다. 오프라인 `GameSave` schema 5 → 6도 같은 방식이다.
3. **콘텐츠 해시가 바뀐다**: `CooperativeWorld.Content`의 hash가 달라진다. 이미 저장된 방(`SavedRoom.World`)은 옛 hash로 열면 "콘텐츠 불일치"로 거부된다(원본 보존).
   선택지: (a) ID를 `cooperative-demo-v2`로 올리고 v1 방은 거부한다 — 합성 콘텐츠이고 운영 데이터가 없으면 가장 단순, (b) v1 hash를 내장해 rules 8 방을 변환 후 계속 받는다.
4. **서버 DB**: `Member.QuestCredit`은 제거 가능(개인 완료 기록으로 대체)하지만 읽기 호환을 위해 한 버전은 무시하며 남긴다. 완료된 방의 `Character.Quests` 정산은 새 규칙으로 정확히 한 번.
5. **와이어**: v5의 `RoomWorldState.Quest`를 **수신자 본인의 단계**로 바꾸고(필드 모양은 같음), 파티원의 단계가 필요하면 선택 필드 `PartyQuest`를 더한다.
   의미가 바뀌므로 프로토콜을 v6으로 올릴지, 서버·클라이언트 같은 빌드 정책(이미 요구)에 기대어 v5 의미를 바꿀지 결정이 필요하다.
   `RoomFrames.Create`의 델타 규칙은 배우·아이템만 패치하므로, 퀘스트 단계 변경은 기존처럼 `World` 비교로 **전체 프레임**을 보내는 경로를 탄다.
6. **클라이언트(Godot)**: 자기 단계 HUD, NPC 대화 입력은 그대로. 파티원 단계 표시는 선택.

## 5. 단계 제안과 시험

1. Core: 개인 단계, rules 9, 변환 8 → 9, 해시 벡터(독립 직렬화), 재생·저장·세이브 변환 계약, 무할당 계약 유지. 오프라인 스모크는 `PlayerLimit = 1`로 기존 흐름 유지.
2. 서버: 콘텐츠 ID/hash 처리, DB 변환, 크레딧을 개인 완료로 교체, 재시작 정책(#85) 계약 갱신, 네트워크 계약(#82·#84) 재확인.
3. 와이어·클라이언트: v5 의미 변경(또는 v6), Godot HUD, 두 프로세스 인수 시나리오에 "두 사람이 따로 수락·완료"를 추가.
4. 문서: `COOPERATIVE_WORLD.md`, `ONLINE_MODES.md`(Open 파일은 변경 없음 — 완료 횟수는 이미 개인 단위), `WORK_PLAN.md`.

필수 시험: 각자 다른 tick에 수락, 같은 tick에 두 사람 수락, 한 명만 완료한 뒤 재시작, 완료 전 사망자는 크레딧 없음, 8 → 9 변환 해시 일치, 옛 hash 방의 거부 또는 변환,
기존 공유 퀘스트 시나리오(전원이 말을 거는)가 개인 단계에서도 같은 최종 결과를 내는지.

## 6. 결정이 필요한 질문

1. **A로 진행해도 되는가?** (B/C는 비권장 이유가 위와 같다.)
2. **처치 진행은 공유로 두는가?** 개인 처치 기여(누가 죽였나)까지 요구하면 규칙이 훨씬 커진다. 합성 월드에는 몬스터가 2마리뿐이다.
3. **완료 보상은 본인 체력 회복만인가?** 지금은 파티 전원 회복이다. 파티 보너스를 남길지.
4. **기존 `cooperative-demo-v1` 방을 이어 받을 필요가 있는가?** 없다면 ID를 v2로 올리고 v1 방은 거부(원본 보존)하는 것이 가장 안전하고 작다.
5. **프로토콜**: `opend2.room.v5`의 `World.Quest` 의미를 바꿀지, `v6`을 만들지. 서버·클라이언트는 같은 빌드 정책이라 v5 유지가 작지만 이미 배포된 `v0.2.0-rc.4` 클라이언트는 새 서버와 섞이지 않는다.
6. **오프라인 저장(schema 5 → 6)을 같은 PR 묶음에서 바꾸는가?** 오프라인 단일 플레이도 같은 Core 필드를 쓴다.

직업·레벨·스킬은 Core에 개념이 없으므로 이 설계의 범위가 아니다. 새 게임 규칙이라 별도 설계가 필요하다.

## 7. 구현 기록 (M5-01d-3)

**권장안 A를 구현했다. 단, `rules 9`가 아니라 `WorldDefinition.PersonalQuests` 표식으로 했다.** 협동 월드는 이미 콘텐츠 해시에 별도 표식
(`cooperative-world-v1`)을 넣어 단일 플레이 월드의 해시·저장을 건드리지 않는 방식이었다. 같은 방식으로 `personal-quests-v1` 표식을 넣었다.

| 제안(4절) | 실제 |
| --- | --- |
| `RulesVersion` 9, 8 → 9 변환, `RestoreLegacy` 목록 확대 | **하지 않음.** `RulesVersion`은 8 그대로다. 개인 월드는 새 콘텐츠라 변환할 옛 데이터가 없다 |
| 오프라인 `GameSave` schema 5 → 6 | **하지 않음.** `Document.PlayerQuests`는 선택 필드이고 값이 없으면 직렬화하지 않아 단일 플레이·공유 월드 파일과 옛 빌드가 영향을 받지 않는다. 개인 월드를 저장할 때만 쓰인다 |
| 상태 해시 직렬화 변경 | 개인 월드에서만 플레이어 수 + 각 단계를 쓴다. 단일 플레이·공유 월드는 기존 바이트와 같다 |
| 콘텐츠 hash 변경 | 표식 때문에 바뀌므로 내장 월드를 `cooperative-demo-v2`로 올렸다 |
| 서버 `Member.QuestCredit` 제거 가능 | 유지하되 의미를 "본인이 완료함"으로 바꿨다. 완료 tick 끝의 생존 추정이 필요 없어졌다 |

결정 질문(6절)에 대해 **가정한 답**(병합 전에 뒤집을 수 있다):
1. A로 진행한다.
2. 처치 진행은 공유한다(개인 처치 기여는 구현하지 않음).
3. 완료 보상은 **본인 체력 회복만**이다(공유 모드는 파티 전원 회복을 그대로 유지).
4. 기존 `cooperative-demo-v1` 방은 이어받지 않는다. v1 월드 방이 든 `realm.json`을 열면 서버는 "콘텐츠 ID/hash 불일치"로 시작을 거부하고 **파일은 그대로 둔다**.
   이전 빌드로 방을 닫거나 데이터 디렉터리를 옮겨야 한다. 합성 콘텐츠이고 운영 데이터가 없다는 전제다.
5. 프로토콜은 v5를 유지하고 `RoomWorldState.Quest`를 **수신자 본인의 단계**로 바꿨다(필드 모양 동일). 이미 배포된 `v0.2.0-rc.4` 클라이언트는 새 서버와 섞어 쓸 수 없다.
   파티원 단계는 보내지 않는다(필요하면 선택 필드 추가).
6. 오프라인 저장 schema는 올리지 않았다.

함께 바뀐 동작: **승리 횟수**는 이제 본인의 퀘스트를 완료한 참가자만 얻는다(이전에는 공유 퀘스트 완료 시 방 전원). Godot HUD 문구는 "Quest:"로 바뀌었고 두 클라이언트
스모크는 호스트만 수락한 뒤 게스트의 퀘스트가 그대로임을 확인하고 게스트가 직접 수락한다. 검증 범위와 한계는 PR 본문에 적었다.
