# 32개 WSS 연결과 다중 방 인수

`eng/check-capacity.py`는 실제 self-contained 서버와 production `OnlineClient`를 사용해
Realm/Open 각각 **8개 방 × 4명 = 32개 동시 WSS 연결**을 검사한다. 33번째 계정은 별도 대기 방의
연결 상한 검사에 사용한다. 테스트 전용 .NET 클라이언트이며 일반 Godot의 PC당 한 클라이언트
정책은 변경하지 않는다. 시스템 CA 저장소도 변경하지 않는다.

```sh
dotnet publish src/OpenD2.Server -c Release -r linux-x64 --self-contained true -o artifacts/network-server -m:1
python eng/check-capacity.py --server-exe artifacts/network-server/OpenD2.Server --seconds 30
```

Windows는 `win-x64`와 `.exe`, Apple Silicon macOS는 `osx-arm64`를 사용한다.
`--seconds`는 모드별 지속 관측 구간(1–3600초, 기본 30초)이다. 설정·전투 준비·연결 회수 시간은
별도다. 기존 등록/방 입장 예산 60회/분을 유지하며, 설정 중 명시적인 429 응답을 받은 요청만
61초 대기 후 한 번 재시도한다. 입력은 자동 재시도하지 않는다. 두 모드 실행에는 설정 대기로
보통 수 분이 추가된다. CI는 기존 3 OS 패키지 작업 안에서 모드별 5초를 검사한다.

## 자동 판정

1. 8개 방의 각 4명에게 올바른 방 ID·배우·호스트 여부·캐릭터 구성의 전체 기준 프레임이 도착한다.
2. 32개 연결이 유지되는 동안 33번째 WSS는 429로 거부된다.
3. 현재 v4 연결(기존 v3 관심 범위와 입력 소비 완료 순번)을 협상하고 모든 클라이언트의 중립 이동 입력 순번이 정확히 1씩 증가한다.
   각 방 4명에게 공통으로 도착한 입력 이후 tick의 전체 상태 해시와 파티 배우·소유 아이템 값이
   일치하고 변경분이 수신된다. 일반 HTTP도 계속 응답한다. v3의 비파티 배우·바닥 아이템 배열은
   수신자별로 다를 수 있으며, 부분 수신 상태에서 전체 상태 해시를 다시 계산하지 않는다.
4. 하나의 WSS를 해제하면 다른 세션이 전체 프레임부터 연결할 수 있다. 다시 32개가 되면 추가
   연결은 거부된다. 클라이언트 해제와 서버의 정리 사이에는 최대 10초의 제한된 대기를 둔다.
5. 전체 연결을 해제한 다음 같은 32개 세션이 다시 연결된다. 전체 기준 프레임·입력 순번으로
   전역 슬롯 또는 세션 예약 누수를 검출한다.
6. 여유 슬롯이 있을 때 다른 방의 구독을 403으로 거부한다. 방 종료가 남은 모든 구독자에게
   404를 전달하고 스트림을 끝내는지 확인한다.

측정 전 가까운 공격자는 정상 전투 명령으로 처치한다. 지속 구간은 중립 입력·스트림 전달 검사이며
전투 부하 시험이 아니다. HTTP 입력은 최대 4개 동시 요청으로 기존 8개 요청 제한 안에서 실행한다.
HTTP 상태 조회는 준비 과정에만 사용하고 지속 관측에서는 WSS를 사용한다.

## 결과와 한계

`artifacts/online/capacity/run-<id>/result.json`에 커밋·dirty 여부·서버 실행 파일 SHA-256·시각과
두 모드 결과를 기록한다. `capacity-realm.json`, `capacity-open.json`에는 6단계 판정,
실제 관측 시간·입력 수·방별 공통 tick 일치 횟수·프레임 수·슬롯 회수 시간·설정 중 제한 대기 횟수,
최근 최대 4096개 HTTP 응답 시간의 p50/p95/max를 기록한다. 실패나 단계 누락은 FAIL과 nonzero다.
비밀 키·PFX·암호·계정 DB는 임시 경로에서 정리하며 결과물에 포함하지 않는다.

### 서버 프로세스 CPU·메모리 (M5-03c)

지속 구간(32개 스트림 유지, 중립 입력) 동안 **실제 서버 프로세스**의 CPU 시간과 작업 집합을 표본한다. `capacity-<mode>.json`에
`server_process_metrics`(`PASS`/`UNAVAILABLE`), `server_cpu_ms`, `server_cpu_percent_of_one_core`(코어 1개 대비 비율),
`server_peak_sampled_working_set_bytes`를 남긴다. 프로세스 정보 접근이 막힌 환경은 `UNAVAILABLE`과 null이며 0으로 채우지 않는다.
`eng/check-capacity.py`는 `PASS`일 때 값이 양수·유효한지, `UNAVAILABLE`일 때 수치가 없는지를 확인한다.

로컬 Windows 11 측정(10초 구간, self-contained 서버, `DOTNET_PROCESSOR_COUNT=2`):

| 모드 | 서버 CPU 시간 | 코어 1개 대비 | 작업 집합 최댓값 | 입력 / 프레임 (구간 합) |
| --- | --- | --- | --- | --- |
| Realm | 1,734 ms | 약 17% | 약 114 MiB | 1,184 / 10,392 |
| Open | 1,547 ms | 약 15% | 약 116 MiB | 1,248 / 10,068 |

- 이는 32개 스트림이 각각 25 Hz로 받고 클라이언트가 초당 약 120개의 입력을 보내는 부하에서의 값이다. 같은 규모에서 프로세스 안 시뮬레이션·프레임
  생성만 잰 값(M5-03b)은 코어 1개의 약 1% 미만이었으므로, **소켓·TLS 암호화·HTTP 처리·수신자별 송신 작업이 서버 CPU의 대부분**이라는 뜻이다.
- 작업 집합은 구간 중 표본의 최댓값이며 GC 고수위나 장시간 증가 추세가 아니다.
- 서버와 시험 클라이언트가 같은 기기에서 돌지만 CPU는 서버 프로세스만 센다. 기기·OS·코어 수에 따라 달라지며 SLA가 아니다.
- 이 표는 Arena 방(8개 × 4인)이다. 같은 부하의 월드 방은 아래 "월드 방 32개 스트림" 절에 있다.

### 월드 방 32개 스트림 (M5-02d)

같은 시험을 **협동 월드 방**(8개 × 4인, v5 스트림)으로도 실행한다. 한 모드의 두 번째 패스이며 Arena 패스에서 로그인한 33개 클라이언트와
캐릭터를 그대로 재사용한다(등록과 운영 설정의 계정 처리 예산 60/min은 한 번만 쓴다). 증거는 `capacity-world-<mode>.json`(`room_kind:
cooperative-world`, `room_interest`/`room_input_progress: v5`)이고 `eng/check-capacity.py`가 6단계, 32개 스트림, 8개 방, 입력 순번·방별 일치 횟수,
서버 프로세스 메트릭을 요구한다. 세부 판정은 Arena와 같다. 33번째 스트림 429, 슬롯 회수 뒤 새 세션 수용, 32개 전체 재연결, 다른 방 403, 방 종료의 404.
월드 입력은 수신자의 지역(Camp)과 방문 epoch(0)를 싣는다. 월드 방은 몬스터를 미리 치울 필요가 없다(플레이어만 Camp에 있다).

로컬 Windows 11 측정(10초 구간, self-contained 서버):

| 모드 | 방 종류 | 서버 CPU 시간 | 코어 1개 대비 | 작업 집합 최댓값 | 입력 / 프레임 (구간 합) |
| --- | --- | --- | --- | --- | --- |
| Realm | Arena | 1,531 ms | 약 15% | 약 119 MiB | 1,312 / 9,962 |
| Realm | 월드 | 844 ms | 약 8% | 약 128 MiB | 1,216 / 9,783 |
| Open | Arena | 1,953 ms | 약 18% | 약 115 MiB | 1,120 / 10,638 |
| Open | 월드 | 969 ms | 약 10% | 약 117 MiB | 1,248 / 9,872 |

- 월드 방의 CPU가 Arena의 절반 정도인 것은 **이번 부하의 차이**로 보인다. Arena 방에는 처치된 몬스터와 전리품이 있는 반면, 월드 시험에서는 플레이어가 모두
  Camp에 서 있고 몬스터는 다른 지역에 있어 지역 관심 범위가 그 상태를 걸러 낸다. 전투가 많은 월드나 여러 지역에 흩어진 파티의 값은 아니다.
- 작업 집합은 두 방식 모두 약 115–130 MiB로 비슷하다. 수치는 단일 실행의 표본이며 분산을 재지 않았다. 반복 측정 없이 모드 간 작은 차이를 해석하지 않는다.
- 월드 방의 포탈 이동·퀘스트 대화 같은 상태 변경이 있는 부하는 포함하지 않는다(중립 이동 입력만).

이 결과는 한 실행 환경에서 **설정된 32개 연결 제한의 기능 검증**이다. 최대 수용 인원, 성능 SLA,
서버의 GC/tick 실행시간(프로세스 CPU 시간만 위에서 측정), 지속 전투·송신 버퍼 포화·혼잡 제어 성능을 입증하지 않는다.
실제 두 PC·WAN·IP 패킷 손실·수동 GUI·2시간 장시간 인수는 계속 **NOT_RUN**이다.
`--seconds` 값을 늘리는 것만으로 이런 항목을 PASS로 바꾸지 않는다.

관련: [2클라이언트 게임플레이](TWO_CLIENT_ACCEPTANCE.md), [TLS 장애/복구](NETWORK_ACCEPTANCE.md).

## 월드 방 v5 프레임의 대역폭 (M5-03a)

`WorldBandwidthContracts`는 월드 방 한 개(4인)의 스트림이 실제로 보내는 **애플리케이션 JSON 크기**를 잰다.
`RoomStream`과 같은 경로(`Realm.StreamState` → `RoomFrames.Create` → 같은 JSON 옵션)를 40 ms tick마다 수신자별로 호출하며,
서버가 25 Hz로 한 프레임씩 보낸다고 보고 초당 값을 환산한다. TLS·WebSocket 프레임·TCP 헤더·재전송은 **포함하지 않는다**.
합성 Camp/Field 콘텐츠이고 네트워크를 거치지 않으므로 WAN 대역폭이나 서버 용량 주장이 아니다.

| 시나리오(250 tick, 수신자 4) | 전체 프레임 | 델타 평균/최대 | 프레임당 평균 | 수신자당 환산 |
| --- | --- | --- | --- | --- |
| 유휴 Camp (연결만 유지) | 1,953 B × 3 | 257 / 258 B | 277 B | 약 6.8 KiB/s |
| 전원 걷기 (모든 배우가 매 tick 변경) | 1,953 B × 251 | — | 1,960 B | 약 47.9 KiB/s |
| 분할 파티 (2명 Camp 유휴, 2명 Field 전투) | 1,955 B × 4 | 333 / 1,174 B | 365 B | 약 8.9 KiB/s |

읽는 법과 관찰:
- 유휴 델타 약 257 B는 변경 항목이 아니라 **고정 필드**(방 ID, tick, 입력 순번, 64자 상태 해시)가 대부분이다. 상태 해시는 tick이 포함되어
  매 프레임 바뀌므로 생략할 수 없고, 유휴 연결의 하한이 수신자당 약 6.8 KiB/s라는 뜻이다. 압축·필드 생략은 아직 하지 않았다.
- 모든 보이는 배우가 매 tick 바뀌면 `RoomFrames.Create`는 패치 대신 **전체 상태**를 보낸다(변경 수가 절반을 넘는 규칙). 4인 방에서는
  전체 프레임이 약 2 KB라 이 선택이 옳지만, 보이는 배우가 늘면 같은 규칙이 비용을 키운다.
- 분할 파티에서 Camp의 두 수신자는 Field의 몬스터·전리품을 받지 않는다(지역 관심 범위). 평균이 낮은 이유다.
- 시험의 한계값은 측정값의 약 1.5배다: 모든 프레임 4 KiB 이하, 유휴 델타 400 B 이하, 걷기 프레임은 전체 상태 + 25% 이하, 분할 델타 2 KiB 이하.
  정확한 바이트 수를 고정하지 않고 필터 누락이나 프레임당 필드 추가 같은 팽창을 잡는다. 의도적 프로토콜 변경으로 넘으면 값을 갱신한다.

측정하지 않은 것: 호스트 CPU/메모리/GC·tick 시간(M5-03의 나머지), 큰 월드·많은 몬스터, 실제 압축(WebSocket permessage-deflate), 8개 방·32개 스트림의 합산 대역폭.

## 통합 중 발견한 화면 상태 수신 순서

macOS Open 패키지 검사에서 HTTP 방 시작 응답을 받은 뒤 대기 중이던 이전 로비 WSS가
도착하면, 화면에서 거부된 상태도 새 수신으로 계산되어 HTTP 전체 상태를 v3 표시 상태로
오인할 수 있었다. 현재는 화면에 실제 적용된 WSS만 새 관측으로 계산한다.
`OPEND2_ACCEPTED_STREAM_ORDERING_PASS`는 늦은 로비·낮은 tick·낮은 입력 순번이 관측 완료를
깨우지 않고, 같은 tick의 정상 v3 상태가 HTTP 전체 상태를 교체하는 순서를 결정적으로 검사한다.
두 Godot 클라이언트 모두 이 검사를 통과해야 `accepted_stream_ordering_ui: PASS`를 기록한다.
