# ONLINE-01: 로그인부터 서버 방 플레이까지

완료 기준은 로그인 → 캐릭터 선택 → 방 생성/참가 → 두 클라이언트의 같은 게임 플레이 → 재접속/서버 저장 복원이다.
이번 구현은 이 흐름의 **자체 서버·최대 4인 전투장 첫 버전**이다. 원작 캠페인 전체, Battle.net 호환,
MPQ 원본 장면의 온라인 플레이, 실제 GUI 인수 완료를 뜻하지 않는다.

## 실행

같은 Actions Migration validation 실행에서 해당 OS의 `OpenD2-M2-*` 클라이언트와
`OpenD2-server-*` 서버 아티팩트를 받는다. 바깥 아티팩트 ZIP과 내부 패키지 ZIP/tar.gz를 각각 푼다.
서버 메타데이터의 SHA256과 파일 크기를 대조한다. 서버/클라이언트 모두 자체 런타임을 포함하며
Godot 편집기, .NET SDK, Python, MPQ, NPC 모델이 이 전투장 실행에 필요하지 않다.
macOS 서버는 CI 실행 호스트 아키텍처용이며 클라이언트는 기존 universal 패키지다.
서버 파일명/메타데이터의 osx-arm64 또는 osx-x64를 실제 장치에 맞춘다.

서버 폴더에서 실행한다. `--data`는 기존 게임 설치/사용자 프로필과 분리된 전용 저장 폴더다.

```sh
# Linux/macOS. macOS 개발 빌드는 서명/공증되지 않았다.
./OpenD2.Server --urls http://127.0.0.1:5080 --data ./realm-data
# Windows PowerShell
.\OpenD2.Server.exe --urls http://127.0.0.1:5080 --data .\realm-data
```

클라이언트 실행 → **Online** 탭 → 서버 주소 → Register 또는 Login → Create character → 캐릭터 선택.
첫 클라이언트는 Create room, 두 번째 계정은 Refresh → 같은 방 선택 → Join.
방장이 Start를 누르면 같은 전투장에서 함께 플레이한다. 한 계정은 동시에 방 하나만 점유한다.

- 이름: ASCII 영문/숫자/밑줄/하이픈 3–24자. 계정명은 대소문자 구분 없이 정규화.
- 계정 비밀번호: 12–128자. 방 비밀번호는 비우거나 같은 길이 규칙 사용.
- 계정당 캐릭터 4개, 방당 4명. 첫 버전의 캐릭터는 같은 전투 능력을 가진 이름별 프로필이다.
- 전투장을 클릭해 초점을 준 뒤 WASD/화살표 이동, Space 근접 공격, Q 강타, F 가까운 전리품 줍기.
- 화면의 HP/마나, 두 플레이어, 몬스터, 전리품은 서버 상태를 표시한다. 메뉴/다른 탭으로 옮겨도
  온라인 방은 일시정지되지 않는다. 창/초점을 잃으면 이동 입력은 중단한다.
- Save server progress는 디스크 체크포인트 성공 응답을 기다린다. 연결이 끊어져도 캐릭터 슬롯은
  방에 남는다. 다시 로그인 → 같은 캐릭터/방 Join으로 재접속한다. 새 로그인은 이전 토큰을 폐기한다.
- 시작 전 Leave는 방에서 빠지고, 방장 이탈 시 다음 멤버가 방장이 된다.
  시작 후에는 재접속을 위해 자리를 유지한다. 방장 Close가 전체 방을 종료한다.
- 전투 중 죽은 캐릭터의 부활은 미구현이다. 방을 종료한 뒤 새 방에서 시작한다.
- 방 체크포인트는 위치·체력·마나·몬스터·아이템·입력 순서를 보존한다. **장비/아이템은 방 내부에만 유지**된다.
  방의 몬스터를 모두 처치하고 방장이 닫으면 참가 캐릭터의 승리 횟수를 한 번 기록한다.
  방 간 캐릭터 레벨/장비/원본 퀘스트 진행 이관은 후속 작업이다.

다른 PC에서 접속하려면 신뢰할 수 있는 인증서를 사용한 HTTPS Kestrel 주소를 운영자가 구성해야 한다.
기본은 loopback이며 원격 평문 HTTP를 서버와 클라이언트 모두 거부한다. 인증서 검증 우회 옵션은 없다.
Kestrel 표준 설정(`Kestrel:Endpoints:Https` 및 인증서 설정)을 사용하고 개인 키/비밀번호를 저장소에 넣지 않는다.
현재는 개발/인수용 단일 서버이며 인터넷 공개 서비스 운영 승인을 받은 상태가 아니다.

## 서버 경계와 저장

- `OpenD2.Online`: 엔진 독립 메시지/HTTP 클라이언트와 고정 전투장 정의.
- `OpenD2.Server`: ASP.NET Core 호스트, 계정/세션/캐릭터/방 소유권, 25 Hz 단일 소유자 시뮬레이션.
- 클라이언트는 입력 의도만 보낸다. actor/tick/체력/아이템 결과는 클라이언트가 지정하지 못한다.
  알 수 없는 JSON 필드, 타 계정 캐릭터, 타인 방, 역행 sequence, 잘못된 이동/대상은 거부한다.
- 이동 입력은 500ms lease다. 15초 동안 모든 멤버의 상태 조회가 끊기면 방 시뮬레이션을 멈춘다.
  해당 시간까지 멤버는 세계에 남아 공격받을 수 있다. 재시작 시 지속 이동/미처리 명령을 해제한다.
- 계정 암호와 선택 방 암호는 개별 랜덤 salt + PBKDF2-SHA256 600,000회로 저장한다.
  세션 토큰은 256bit 난수, 메모리 전용, 8시간 만료이며 서버 재시작 시 재로그인해야 한다.
- 요청 본문 8KiB, 동시 연결 64, 동시 요청 8, 게임 요청 전체 1,000/s, 암호 처리 요청 전체 60/min.
  한 서버당 계정 256/방 32 및 JSON 16MiB 상한이다. 이는 성능 보장 수치가 아닌 거부 한도다.
- 디스크 파일은 단일 writer lock과 임시 파일 flush + rename으로 교체한다. 실패한 저장 뒤에는 요청을
  거부하고 서버 루프를 종료한다. 읽을 수 없는 기존 DB는 초기화하거나 덮어쓰지 않는다.
- 계정/캐릭터/방 구성 변경 및 수동 Save는 저장 성공 뒤 응답한다. 게임 tick은 1초 간격 저장이므로
  강제 종료 시 최근 약 1초의 진행은 유실될 수 있다. 다중 프로세스 DB/복제/백업 회전은 미구현이다.
  정상 종료는 마지막 체크포인트를 시도한다. 데이터 폴더 접근권한과 별도 백업은 운영자가 관리한다.

## 검증과 실제 GUI 인수

자동 검사:

```sh
dotnet run --project tests/OpenD2.OnlineTests -c Release
python eng/check-online.py                         # 실제 HTTP 세 접속/권한/저장/강제 재시작
python eng/check-online.py --godot auto            # 독립 Godot 프로세스 2개
python eng/pack-online-server.py                   # 배포 클라이언트 생성 후 서버 publish/압축/해제/실행
```

Migration validation은 기존 380개 계약/엄격 ERROR 검사/OS 패키지 smoke를 유지한다.
추가로 소유권·전투·재접속·저장 실패 계약과 **압축 해제한 서버 + 클라이언트 2개**의 로그인,
캐릭터, 방 생성/참가, 시작, 이동 전파를 실행한다. `artifacts/online/result.json`과 두 Godot 로그,
OS별 서버 ZIP/체크섬을 아티팩트로 보존한다. 테스트 계정 DB/비밀번호/토큰은 업로드하지 않는다.
헤드리스 두 프로세스의 통과는 실제 화면·키보드·멀티 PC 네트워크 인수와 별도다.

Linux 일반 클라이언트의 간헐적 시간 초과도 별도로 재현했다. 실행
`38049309902`의 `export-smoke.stack.log`는 장면 재시작 중 `SceneAudio.Tone()`의
네이티브 호출에서 메인 스레드가 멈춘 것을 기록한다. Godot의 Stop은 믹서 페이드아웃을
예약하므로 생성기 스트림을 즉시 해제하면 안 된다. 생성기 재생 객체의 native metadata가
스트림 참조를 소유하게 해 믹서가 재생 객체를 최종 해제할 때까지 수명을 유지한다.
Linux CI는 일반 클라이언트 시작·장면 전환·오디오 정리·종료를 8회 추가 반복한다.
각 실행은 기존 60초 제한, 모든 준비 마커, 종료 코드와 ERROR 검사 기준을 그대로 사용한다.
출력을 즉시 기록하고, 시간 초과 전의 제한된 스택 수집 결과도 검증 아티팩트에 보존한다.

실제 GUI/그록봇 인수: **NOT_RUN**. 다음 증거가 필요하다.

1. 서로 다른 두 계정으로 일반 창을 실행해 로그인/캐릭터 선택/방 목록과 같은 방 입장을 캡처한다.
2. 두 화면에서 동시 이동, 충돌, 몬스터 공격/피해/전리품, 잘못된 방 암호를 확인한다.
3. 한 창의 초점/네트워크를 잃은 뒤 이동 정지와 로그인/같은 캐릭터 재접속을 확인한다.
4. 저장 후 서버를 재시작하고 두 계정의 캐릭터/방/위치/체력/전리품 복원을 비교한다.
5. 창 크기/DPI/키 입력/장시간·지연·끊김을 검사하고 OS, 서버/클라이언트 커밋, 화면, 로그를 남긴다.

## 두 클라이언트 플레이 통합 검증

`eng/check-online.py`는 서로 다른 계정의 독립 Godot 프로세스 2개와 실제 서버를 실행한다.
입력은 실제 클라이언트 HTTP 경로로 전달하며, 서버 테스트 전용 API나 결과 조작은 사용하지 않는다.

- 같은 방 입장·시작, 호스트 이동을 양쪽에서 관측.
- 호스트 일반 공격과 게스트 스킬·마나 감소를 양쪽에서 관측.
- 몬스터 처치·전리품 생성, 호스트 획득과 게스트의 소유 아이템 탈취 거부.
- 호스트 연결 해제 후 이동 lease 만료·정지, 같은 계정/캐릭터 재접속과 아이템 유지.
- 두 클라이언트가 실행 중인 상태에서 서버 강제 종료·재시작, 양쪽 재로그인 및 위치·체력·아이템 복원.
- 방 종료가 양쪽에서 접근 불가로 반영됨을 확인.

실행별 `gameplay-*` 폴더에 양쪽 로그, 판정 JSON, 방/전투/전리품/재접속/복원 상태를 남긴다.
검사 입력별 서버 상태는 `*-actions.jsonl`로 보존한다. CI `38053719315`에서 게스트가
호스트의 직선 접근을 막아 대기 중 죽는 상황을 재현했다. 검사 드라이버는 실제 공격 사거리에서
공격하고 살아 있는 캐릭터를 피해 접근한다. 기록된 좌표와 추가 몸체 충돌 배치의 회귀 검사는
실제 Core 이동·충돌·공격으로 판정하며, 캐릭터 위치·체력이나 서버 규칙을 조작하지 않는다.

개인 서버 DB, 암호와 토큰은 아티팩트에 포함하지 않는다. 클라이언트 비정상 종료, ERROR 로그,
증거·완료 마커 누락, 서버 재시작 누락, 단계/전체 제한 시간 초과는 실패다.

Windows/Linux/macOS는 압축 해제한 실제 배포 서버와 클라이언트 2개로 이 시나리오를 실행한다.
Linux CI는 추가로 Xvfb에서 두 창을 렌더링하고 각 클라이언트의 5단계 PNG를 저장한다.
두 창 렌더링 자동 검사는 `rendered`로, 사람이 직접 입력하는 GUI 인수는 `gui`로 구분한다.
자동 시나리오는 클라이언트 명령 경로를 호출하므로 마우스/키보드 포커스·메뉴 클릭 전체를 검증하지 않는다.
물리 PC 2대·실제 그래픽/오디오 장치·WAN/TLS·장시간 플레이 인수도 별도다.

```sh
# 개발 소스: 먼저 서버 Release와 Godot 클라이언트 Debug를 빌드한다.
python eng/check-online.py --godot auto
# 디스플레이가 있는 환경에서 창 두 개와 단계별 스크린샷 검사
python eng/check-online.py --godot auto --windowed --output artifacts/online/rendered
# Linux 배포 패키지: 헤드리스 + 창 렌더링을 모두 검사
OPEND2_ONLINE_RENDERED=1 xvfb-run -a -s "-screen 0 2400x1100x24" python eng/pack-online-server.py
```

로컬 헤드리스 두 클라이언트 전체 시나리오는 통과했다. 로컬 창 검사는 실행 환경의 Unix 소켓
생성 제한으로 Xvfb가 디스플레이를 열지 못해 실패했으며, Linux Actions에서 별도로 검증한다.
실제 수동 GUI/멀티 PC 인수는 **NOT_RUN**이다.

### ONLINE-06 유저 간 음성대화 고도화 (계획, 미구현)

- 같은 방에 입장한 계정만 참가하는 음성 채널과 참가자 발화 표시. 방 이탈·종료·세션 만료 시 음성 연결도 해제한다.
- 기본 마이크 꺼짐, 사용자 동의 후 참여, 눌러 말하기/음성 감지 선택, 전체 음소거와 사용자별 음소거·볼륨.
- 마이크·출력 장치 선택, OS 권한 거부/장치 분리 처리, 에코·잡음 억제와 입력 수준 확인.
- WebRTC 기반 전송을 우선 검토한다. 4인 직접 연결과 TURN 중계의 대역폭·CPU·비용을 측정하고,
  인원이 늘어날 경우 SFU 방식과 비교한다. 미디어 전송은 게임 상태 처리 루프와 분리한다.
- 기존 로그인·방 권한으로 신호 교환을 인증하고 음성 전송을 암호화한다. 기본 녹음/저장은 하지 않으며,
  음성 차단·재접속·잘못된 방 접근·네트워크 변경·패킷 손실 상황을 검증한다.
- 자동 검사: 방/세션 권한, 음성 연결 상태 전이, 재접속과 지연·손실 모의 시험. 실제 마이크·스피커 인수와 구분한다.
- 실제 인수: Windows/Linux/macOS의 서로 다른 PC에서 2–4인 대화, 말 겹침·에코·눌러 말하기,
  음소거/볼륨·장치 전환·방 이동/퇴장·장시간 통화와 게임 중 FPS/지연/서버 부하를 확인한다.
  실제 장치 음성 품질 검증은 현재 **NOT_RUN**이다.
