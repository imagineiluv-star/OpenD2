# TLS 통신 장애와 제한된 부하 검증

`eng/check-network.py`는 실제 self-contained 서버와 production `OnlineClient` 두 개를
사용한다. Realm/Open 각각 게스트 경로에 **암호화된 바이트만 전달하는 loopback TCP 프록시**를
두며 TLS 종료/복호화/인증서 검증 우회를 하지 않는다. 일반 Godot 클라이언트의 PC당 1개
정책과 테스트 예외 코드는 변경하지 않는다.

## 실행

같은 커밋의 .NET SDK와 서버 실행 파일을 준비한 뒤 저장소 루트에서 실행한다.

```sh
dotnet publish src/OpenD2.Server -c Release -r linux-x64 --self-contained true -o artifacts/network-server -m:1
python eng/check-network.py --server-exe artifacts/network-server/OpenD2.Server --seconds 30
```

Windows는 `win-x64`와 `OpenD2.Server.exe`, Apple Silicon macOS는 `osx-arm64`를 사용한다.
`--seconds`는 모드별 **마지막 지속 실행 구간**의 길이이며 1–3600초다. 기본은 30초다.
인증서·서버·방 설정 및 기존 TLS 계약 수행 시간은 추가된다. `--output`으로 증거 경로를
바꿀 수 있다. 각 실행은 새 `run-<id>`를 사용하며 비밀 키·PFX·암호·계정 DB는 임시 폴더에서 삭제한다.

기존 `--tls-server` 계약과 3 OS 패키지 CI에도 각 모드 5초 지속 실행을 포함한
전체 장애 시나리오를 연결했다. 별도의 중복 CI 작업은 만들지 않았다.

## 자동 판정

1. 직접 연결 호스트와 프록시 경유 게스트가 동일 CA를 검증하고 같은 방의 WSS를 구독한다.
2. 암호화 바이트를 최대 1024바이트로 나누고 각 쓰기에 5/10/15ms 지연을 순환 적용한다.
   실제 지연 쓰기가 발생하고, 입력 접수·상대 이동 관측·v2 변경분 복원이 계속되는지 확인한다.
3. 게스트의 서버→클라이언트 전달을 중단하고 이동 배치를 보낸다. 호스트 WSS로 배치가
   적용됐음을 확인하지만 게스트 HTTP 응답은 아직 완료되지 않아야 한다.
4. 그 상태에서 호스트의 tick이 계속 진행하고 HTTP API도 응답하며, 게스트의 갱신되지 않은
   이동 lease가 만료되는지 확인한다. 프록시 내부에서 실제 대기 중인 전달 작업도 확인한다.
5. 게스트의 기존 HTTP/WSS TCP 연결을 함께 끊는다. 입력 응답·WSS가 실제 전송 오류를
   알린 뒤 재로그인·같은 캐릭터/방/actor 재입장·전체 기준 프레임 수신을 확인한다.
   입력 순번이 정확히 2만큼 증가해야 하므로 응답 유실 입력의 누락·중복 접수를 검출한다.
   재접속 후 새 이동 입력도 상대 WSS에서 관측해야 한다.
6. 지연 경로를 다시 켜고 지정 시간 동안 중립 이동 입력과 지속 WSS 수신을 반복한다.
   두 클라이언트가 동일 tick의 동일 상태 해시를 받는지 매 입력마다 비교한다.
7. 새 게스트 세션에 수신을 전혀 하지 않는 TLS WebSocket을 연결한다. 이 검사 클라이언트의
   자체 keepalive는 끄고, 연결 해제·취소·읽기·재로그인 없이 같은 토큰의 중복 연결이 먼저
   409로 거부되는지 확인한다. 정상 호스트의 WSS tick과 HTTP 응답을 계속 검사하면서
   서버가 무응답 연결을 정리하여 같은 토큰의 새 연결을 20초 이내에 받아들이는지 확인한다.
8. 그 새 연결의 첫 v3 프레임이 전체 기준 상태이며 방·캐릭터·actor·입력 순번이 보존되는지,
   같은 세션의 새 입력 하나가 정확히 한 번 접수되어 WSS로 관측되는지 확인한다.

7–8번은 production `OnlineClient`의 수신 제한 시간이 서버 종료로 오인되지 않도록
검사 전용 `ClientWebSocket`을 사용한다. 실제 서버의 5초 ping/5초 pong 정책을 유지한다.
연결별 공개 CA/호스트 이름/TLS 검증을 그대로 수행하며, 수신 중단은 암호화 종료나 검증 우회가 아니다.

대기에는 명시적인 상한이 있다. 실패·단계 누락·모드 불일치·측정 시간 부족이면 종료 코드가
0이 아니며 최종 결과는 FAIL이다. 프록시의 연결 수와 버퍼, 관측 상태 이력도 제한한다.

## 증거와 측정 범위

`run-<id>/result.json`에 커밋/dirty 여부·시각·Realm/Open 결과를 기록한다.
`network-realm.json`, `network-open.json`에는 단계·프록시 지연/정체/단절 횟수,
전달 암호화 바이트 수·WSS 프레임 수·동일 tick 해시 일치 횟수·복구 시간을 남긴다.
`silent_stream`에는 무응답 연결 정리 후 재접속까지의 관측 시간, 409 응답 횟수와 복구된 입력
순번을 기록한다. 이 시간은 반복 연결 시도 간격을 포함하며 정확한 서버 내부 종료 시각이나 SLA가 아니다.
실패·8단계 누락·무응답 연결 검증 누락은 실행 도구에서 FAIL로 처리한다.

마지막 지속 실행 구간의 HTTP 요청 시작→응답 완료 p50/p95/max와 서버 프로세스 CPU 시간,
표본 WorkingSet 최댓값을 기록한다. CPU/메모리는 시험 서버 프로세스 전체 값이며 클라이언트
비용이나 GC/tick 실행시간이 아니다. 프로세스 통계 접근이 제한된 환경은
`server_process_metrics: UNAVAILABLE`과 null 값으로 남기며 수집 성공으로 표시하지 않는다. 프록시 바이트 수는 TCP/TLS를 통해 전달한 암호문 바이트이며
NIC 패킷/헤더·재전송량을 포함하지 않는다. 지연 수치에 성능 SLA를 적용하지 않는다.

이 테스트는 Godot 화면이나 사람이 조작하는 GUI를 실행하지 않는다. 두 Godot 프로세스의
초대·게임플레이·재접속은 [별도 인수 실행기](TWO_CLIENT_ACCEPTANCE.md)가 담당한다.

## 협동 월드 방의 응답 유실과 무응답 수신자 (M5-02a/b)

Arena 방의 입력은 위치를 바꾸는 이동뿐이라 응답이 유실돼도 서버 커서만 맞추면 된다. 협동 월드의 포탈은
**수락된 입력이 지역과 방문 epoch를 바꿀 수 있어** 응답을 잃은 클라이언트가 결과를 모른다.
`CooperativeNetworkContracts`는 월드 서버(`world-realm`, `world-open`)에서 위의 바이트 프록시를
그대로 사용해 다음을 판정한다. 별도 CI 작업은 만들지 않고 기존 `--tls-server` 계약에 포함했다.

1. 호스트(직접)와 게스트(프록시 경유)가 같은 월드 방의 v5 WSS를 구독한다.
2. **거부된 포탈**: 사거리 밖 게스트가 `[포탈 Interact, 이동]` 배치를 보내고 응답이 유실된다.
   상대 호스트가 이동을 관측해 서버 수락을 증명한 뒤 연결을 끊는다. 재로그인·재입장 결과는 커서가 정확히
   2 증가하고 지역·방문 epoch는 그대로여야 한다(수락된 입력이 곧 포탈 성공은 아니다).
3. 지연/분할 경로에서 게스트 이동 한 걸음의 v5 변경분을 복원하고 호스트와 같은 tick의 상태 해시를 비교한다.
4. **성공한 포탈**: 사거리 안에서 포탈 입력의 응답이 유실된다. 호스트가 게스트의 지역 변경을 관측한 뒤
   끊는다. 복구 결과는 새 지역, `0 < regionEpoch ≤ 현재 tick`, 커서 정확히 1 증가여야 한다.
5. 유실된 입력을 그대로, 새 순번에 옛 지역/epoch를 붙여, 또는 옛 방문 입력이 든 배치로 다시 보내면 모두
   409로 거부되고 커서·지역·epoch가 변하지 않아야 한다(포탈 이중 실행 방지).
6. 복구 뒤 새 입력이 분할된 파티에 전달되고, 게스트 쪽에만 몬스터가 보이며 두 WSS의 해시가 같아야 한다.
7. **무응답 수신자(M5-02b)**: 게스트의 새 세션이 v5 월드 WSS를 열고 아무것도 읽지 않는다(자체 keepalive 끔). 같은 토큰의
   중복 연결은 먼저 409로 거부되고, 서버가 이 연결을 정리해 같은 토큰의 새 연결을 20초 안에 받아들이는 동안 호스트의
   WSS tick과 HTTP는 계속 응답한다. 새 세션은 월드 콘텐츠를 다시 밝히며 입장해야 한다(세션이 바뀌면 월드 확인도 새로 필요).
8. 새 연결의 첫 프레임은 **전체 v5 기준 상태**여야 하고 콘텐츠·지역·방문 epoch·행위자·입력 순번이 보존되어야 한다.
   같은 세션의 새 월드 입력(지역/epoch 포함) 하나가 정확히 한 번 접수되어 WSS로 관측된다.

합성 전송 시험 `STREAM SEND DEADLINE`도 Realm/Open 각각 월드 방을 추가했다(4개 조합). 한 수신자의 송신이 멈춘 동안 호스트가
포탈을 지나가며, 멈춘 송신은 스냅샷을 쌓지 않고 정상 상대를 막지 않으며 2초 제한으로 취소·abort된 뒤, 같은 토큰으로 다시 연 스트림이
**포탈 이후의 현재 상태**(tick ≥ 10, 파티원은 새 지역에 보이고, 자기 방문 epoch 0, 다른 지역 몬스터는 필터링)의 전체 기준
상태로 시작해야 한다. 이 시험은 모의 전송이며 실제 OS 송신 버퍼 포화가 아니다.
증거는 `network-world-<mode>.json`(8단계·프록시 지연/정체/단절 횟수·전달 바이트·복구 횟수·`silent_stream`)이다.
`eng/check-network.py`는 8단계, 복구 2회, 해시 일치 2회 이상, 무응답 연결 정리(409 응답 ≥ 1, 20초 미만)와
NOT_RUN 항목을 확인하며 어긋나면 FAIL이다. `silent_stream.EvictionMs`는 반복 연결 시도 간격을 포함하며 SLA가 아니다.
시간 제한(120초)과 단계 누락은 실패다. 유효한 보류는 **이미 열린 HTTP 연결**을 재사용해야 하므로 시험은
보류 직전에 연결을 데운다(새 TLS 핸드셰이크는 보류된 하향 경로에서 멈춰 서버에 입력이 닿지 않는다).

범위 밖: 실제 OS 송신 버퍼 포화, pong에는 응답하지만 느리게 소비하는 수신자, IP 패킷 손실·재정렬·WAN, 두 PC, 수동 GUI는 **NOT_RUN**이다.
월드 방의 재시작·강제 종료 중 포탈 입력은 [COOPERATIVE_WORLD](COOPERATIVE_WORLD.md#재시작과-강제-종료-정책--m5-02c)의 정책 계약이, 월드 방의
32개 스트림 용량은 [STREAM_CAPACITY](STREAM_CAPACITY.md)의 월드 절이 다룬다.

## 송신 제한 계약과 미검증 항목

일반 `dotnet run --project tests/OpenD2.OnlineTests -c Release`는 Realm/Open 각각
production `RoomStream.Run`에 취소 가능한 **모의 WebSocket 전송**을 연결한다.
한 송신이 멈춰 있는 동안 추가 상태를 송신 대기열에 쌓지 않고 정상 상대의 tick 전달이
진행되는지, 기존 2초 송신 제한으로 취소·abort 후 같은 세션 예약이 해제되는지,
재연결이 새 전체 기준 상태부터 시작하는지 확인한다.
`STREAM SEND DEADLINE PASS`는 이 결정적 계약 검사 결과이며 실제 TLS 버퍼 포화 측정이 아니다.
위 실제 TLS 무응답 검사와 함께 기존 3 OS CI에서 실행한다. 일반 클라이언트 하나 정책과
서버 연결 수·등록·방 입장 제한은 변경하지 않는다.

- 바이트 분할·지연은 IP 패킷 분할/손실, 지정 RTT/지터 또는 실제 WAN 에뮬레이션이 아니다.
- 짧은 downstream 정체와 실제 TLS 무응답 연결 종료는 확인한다. 모의 송신 정체는 2초 제한
  및 예약 정리를 확인한다. **실제 OS 송신 버퍼 포화**, pong에는 응답하지만 게임 상태를
  느리게 소비하는 클라이언트, 혼잡 제어 상한·메모리 고수위 실측은 여전히 별도다.
- 32개 스트림/다중 방의 연결 상한·회수는 [별도 인수 도구](STREAM_CAPACITY.md)로 검사한다.
  최대 서버 용량, GC/tick 실행시간, 실제 패킷 손실·재정렬·중복은 별도다.
- 물리적 두 PC LAN/WAN, 실제 Wi-Fi 변경·공유기/NAT, 수동 GUI, 2시간 이상 장시간 인수는
  **NOT_RUN**이다. `--seconds`를 늘려도 이런 항목을 자동으로 PASS 처리하지 않는다.
