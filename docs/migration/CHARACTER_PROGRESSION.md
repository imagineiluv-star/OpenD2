# 직업·레벨·스킬 기반 (M5-04a)

**상태: 구현됨(규칙·표 로더·서버·Open 파일). Godot UI와 원본 값 대조는 미구현.** Diablo II의 구조를 먼저 그대로 따른다:
직업 7종, 능력치 4개, 레벨 1–99, 레벨당 능력치 5점과 스킬 1점, 스킬 선행 조건. 규칙은 Core에, 숫자는 표에 둔다.

> **이 PC에는 Diablo II 설치본이 없어 원본 TXT와 한 번도 대조하지 않았다.** 내장 `preview` 표의 시작 능력치·생명/마나 증가율은
> 알려진 직업 특성의 모양만 따른 값이고 경험치 곡선은 단순한 2차식이다(레벨 2 = 500, 레벨 99 = 2,425,500). **원본 값이 아니다.**
> 원본 값은 소유자의 설치본에서 `CharStats.txt`·`Experience.txt`·`Skills.txt`로 읽어야 한다(아래 "원본 표"). 로더가 읽는 열의
> 의미와 `Experience.txt` 행 해석은 문서 기억에 근거한 가정이며 실제 파일로 확인되기 전까지 `unverified`다.

## 규칙 (`OpenD2.Core/Progression.cs`)

| 항목 | 규칙 |
| --- | --- |
| 직업 | Amazon, Sorceress, Necromancer, Paladin, Barbarian, Druid, Assassin. 시작 능력치(힘·민첩·활력·에너지)와 기본 생명·마나·스태미나가 직업마다 다르다 |
| 레벨 | 1–99. 경험치 표는 "그 레벨에 도달하는 데 필요한 누적 경험치"이고 레벨 1은 0이다. 표는 직업별로 엄격히 증가해야 한다 |
| 포인트 | 레벨이 오를 때마다 능력치 `StatPerLevel`(기본 5)점과 스킬 1점. 한 번에 여러 레벨이 오를 수 있다. 최대 레벨에서는 경험치가 더 쌓이지 않는다 |
| 능력치 | 포인트 1점을 힘·민첩·활력·에너지 중 하나에 쓴다. 되돌리기(재분배)는 없다 |
| 스킬 | 직업 스킬만, 첫 점은 요구 레벨 이상, 선행 스킬(최대 3개)이 각각 1점 이상, 스킬 최대 레벨(≤60) 이하. 선행 사슬은 순환할 수 없고 같은 직업 안에서만 이어진다 |
| 생명·마나·스태미나 | 직업 기본값 + (레벨 − 1) × 레벨당 증가 + (시작 값보다 더한 활력/에너지) × 능력치당 증가. **증가율은 4분의 1 단위로 합산한 뒤 한 번 내림**(1.5/레벨은 1레벨 +1, 2레벨 +3) |
| 회계 | 어떤 `CharacterProgress`든 `(능력치에 더한 점) + 남은 능력치 점 = (레벨−1) × 레벨당 점`, `(스킬에 쓴 점) + 남은 스킬 점 = (레벨−1)`, 경험치가 레벨 구간 안, 스킬이 정렬·유일·유효. `Progression.Validate`가 규칙으로 만들 수 없는 값을 거부한다 |

## 원본 표 (`OpenD2.Assets/CharacterTables.cs`, `AssetAudit --character-txt`)

`CharacterTables.Load(read)`는 소유자의 TXT를 `lod-1.10f` 프로필로 읽어 `ProgressionTables`와 `SkillTable`을 만든다(파일 크기·행·열 한도,
SHA-256 출처 기록). 읽는 열(가정):

| 파일 | 열 → 필드 |
| --- | --- |
| `charstats.txt` | `class`(7개 이름, `Expansion` 행은 건너뜀), `str` `dex` `vit` `int`(에너지) → 시작 능력치, `hpadd` → 기본 생명, `int` → 기본 마나, `stamina` → 기본 스태미나, `LifePerLevel` `ManaPerLevel` `StaminaPerLevel` `LifePerVitality` `ManaPerMagic` `StaminaPerVitality` → 4분의 1 단위 증가율, `StatPerLevel` → 레벨당 능력치 점 |
| `experience.txt` | `MaxLvl` 행 → 직업별 최대 레벨, 행 `N`의 직업 열 → 레벨 `N + 1`에 필요한 누적 경험치(행 0 = 0). 모든 행 0…`MaxLvl`−1이 있어야 한다 |
| `skills.txt` | `charclass`(`ama` `sor` `nec` `pal` `bar` `dru` `ass`; 비어 있으면 몬스터·아이템 스킬로 보고 무시), `skill`(이름), `*Id`, `reqlevel`, `maxlvl`, `reqskill1..3`(이름으로 같은 직업의 스킬을 가리킴) |

알 수 없는 직업·중복·빠진 행/열·잘못된 수·가리키는 곳이 없는 선행 조건·순환은 파일/줄 번호가 있는 `InvalidDataException`이다.
`AssetAudit --character-txt <게임 데이터 디렉터리>`는 JSON(`VersionStatus: "unverified"`, `GameplayValidated: false`)으로 직업·경험치 표·스킬을
출력한다. **이 명령으로 실제 설치본을 한 번 읽어 보고 위 가정이 맞는지 확인하는 것이 다음 단계다.** 서버는 아직 MPQ에서 표를 읽지 않고
`Preview`를 쓴다(`new Realm(..., tables, skills)`로 바꿀 수 있는 자리만 있다).

## 서버

- **캐릭터 생성**: `POST /v1/characters {"name":"…","class":"Amazon"}`. `class`는 이름만 받는다(대소문자 무시; 숫자·공백 거부). 생략하면 **직업 없는 기존 캐릭터**이고
  고정 자원(생명 100/마나 60)과 기존 동작을 그대로 쓰며 경험치를 얻지 않는다. 직업이 있으면 `CharacterInfo.progress`가 응답에 나타난다(없으면 JSON이 기존과 같다).
- **방 시작**: 직업 있는 참가자의 생명·마나가 레벨과 능력치에서 계산된 값이 된다(`GameSimulation.WithPlayerResources`, 첫 틱 전에만).
- **경험치**: 몬스터가 죽으면 **같은 방에서 그 몬스터와 같은 지역에 있는 생존한 직업 캐릭터 전원**이 받는다(거리·파티 보너스 없음). 양은 `Progression.PreviewKillExperience`
  = 몬스터 최대 체력(60 → 60). **원본의 몬스터별 경험치·레벨 차이 보정이 아니다**(시뮬레이션에 몬스터 종류/레벨이 아직 없다). 경험치는 아이템·퀘스트 크레딧처럼
  **방 상태**(`Member.Experience`, 방 저장에 포함)이며 **호스트가 방을 닫을 때** 캐릭터에 정산된다. 정산 중 레벨이 오르면 포인트가 생긴다.
- **포인트 사용**: `POST /v1/characters/{id}/stats {"stat":"Strength"}`, `POST /v1/characters/{id}/skills {"skill":101}`. 방 밖에서만(정산과 경합하지 않도록) 가능하고
  직업이 없거나 포인트가 없거나 규칙에 어긋나면 409, 잘못된 이름/스킬은 400, 남의 캐릭터는 404다. 성공하면 즉시 영속화한다.
- **영속화·무결성**: `Character.Progress`가 `realm.json`에 저장된다. 서버는 시작할 때 모든 진행을 `Progression.Validate`로 검사하고, 규칙으로 만들 수 없는 값(여분의 능력치/스킬
  점, 경험치와 안 맞는 레벨, 다른 직업의 스킬, 선행 없는 스킬)이나 직업 없는 캐릭터/시작 안 한 방의 방 경험치가 있으면 **시작을 거부**한다(자동 보정 없음). 다른 표로 쓴 데이터도 같은 이유로 거부된다.
- **협상**: `/health.characterProgress: 1`(클라이언트 `SupportsCharacterProgress`), `characterFileVersion: 4`. 구형 서버에 직업 지정을 보내면 클라이언트가 먼저 거부한다.

## Open 캐릭터 파일 형식 4

형식 3에 `progress`(직업·레벨·경험치·점·능력치·스킬)가 추가된다. 직업 없는 캐릭터는 `progress`를 쓰지 않는다. 형식 1–3 파일은 원본을 수정하지 않고 메모리에서
이관한다(`progress` 없음). 형식 3 이하에 `progress`가 있으면 어긋난 파일로 거부한다. 파일 자체는 형태만(직업·레벨 범위·스킬 ≤64개) 검사하고,
**점 회계는 받는 서버의 표로 다시 검사**해 다른 규칙으로 만든 파일은 400으로 거부한다. 46개 아이템·8개 퀘스트 기록·64개 스킬 등급이 모두 차도 8 KiB 안에 들어간다(계약으로 고정).
Open의 파일은 사용자가 편집할 수 있으므로 회계가 맞는 가짜 99레벨도 만들 수 있다 — 승리 횟수·아이템과 같은 신뢰 수준이다. Realm은 파일 반입/반출을 거부한다.

## 하지 않은 것

- 원본 값 대조(위 경고), 서버가 설치본 MPQ에서 표를 읽기.
- 스킬 효과: 기존 `PowerStrike`만 있고 스킬 표의 스킬은 포인트를 쌓을 뿐 전투에 영향이 없다. 스킬 레벨 보너스(+스킬), 스킬 레벨별 수치.
- 능력치의 전투 효과: 힘/민첩이 피해·명중·방어에 주는 영향, 장비 요구 능력치, 스태미나 소모, 마나 회복 속도 연동. 지금은 **생명·마나 최대치**만 바뀐다.
- 몬스터 종류·레벨·난이도, 경험치의 레벨 차이 보정, 파티 경험치 분배 규칙, 사망 페널티, 스킬/능력치 재분배(리스펙).
- 방 안에서의 즉시 레벨업(정산은 방을 닫을 때), Godot의 직업 선택·능력치/스킬 창·HUD 경험치 막대, 클라이언트의 캐릭터 생성 화면 변경.
- 이미 만든 캐릭터에 직업 부여(직업 없는 캐릭터는 그대로 직업 없음).

## 검증

- Core `ProgressionContracts`(테스트 13개): 표/선행 사슬 생성 거부, 경계 경험치, 레벨 상한과 오버플로, 능력치·스킬 지출, 4분의 1 단위 합산, 위조 진행 거부, 무작위 400회 연산 × 7직업의 회계 불변식, 방 시작 자원 훅, 합성 TXT 왕복과 거부.
- 온라인 `CharacterProgressContracts`(Realm·Open 각 1회 + Open 파일): 직업 이름 검증, 직업별 시작 자원, 지역·생존·직업 규칙으로 나뉜 경험치, 재시작을 거친 정산, 지출 거부, 영속화, 변조 문서 거부, 다른 표 거부, 형식 4 왕복·위조·크기.
- 기존 계약 갱신: Open 파일을 쓸 때 형식이 4가 된다(`PersonalQuestContracts`, `OpenItemTransferContracts`).
- 변이 시험: 규칙을 하나씩 깨뜨려 새 계약이 실패하는지 확인했다(결과는 PR 본문 표). 이 PC에는 네이티브 MPQ·NPC 런타임이 없어 Core 계약 14개가 처음부터 실패한다(진행 기능과 무관, CI에서는 통과).
