# 월드 방 호스트 CPU·저장 비용 측정 (M5-03b)

`WorldHostLoadContracts`는 8개 방 × 4인 = 32 수신자(문서화된 32개 스트림 목표)의 협동 월드를 **한 프로세스, 한 스레드**에서
150 tick 돌리며 호스트가 40 ms tick마다 쓰는 비용을 잰다. 모든 플레이어가 걷고 있어(입력 갱신 8 tick마다) 방마다 매 tick 실제 일이 있다.
시험은 방이 정말 150 tick 진행했고 32명이 전부 움직였는지 먼저 확인한 뒤에만 수치를 인정한다.

## 무엇을 재는가

| 구간 | 내용 |
| --- | --- |
| `Realm.Tick()` | 이동 lease 처리, 모든 방의 시뮬레이션 1 step, 이벤트 처리, 스냅샷 무효화 |
| 프레임 생산 | 수신자 32명 각각의 `StreamState`(관심 영역 투영 포함) → `RoomFrames.Create` → JSON 직렬화. `RoomStream.Push`와 같은 경로 |
| `Realm.Checkpoint()` | 서버 루프가 25 tick(약 1초)마다 부르는 저장: 모든 방의 JSON, `fsync`, 원자적 교체. **`Tick`·입력·스트림 읽기와 같은 전역 락 안**에서 실행 |

소켓, TLS, WebSocket 송신, HTTP 입력 처리, 수신자별 송신 대기는 **포함하지 않는다**. 값은 시험 기기에 따라 달라진다.

## 측정 결과 (Windows 11, NVMe SSD, 3회 반복에서 일관됨)

| 항목 | 중앙값 | p99 / 최대 |
| --- | --- | --- |
| `Realm.Tick()` (8개 방) | 0.01 ms | 0.02 ms |
| 프레임 32개 생산 | 0.30 ms | 약 1.0 ms / 최대 2.1 ms |
| tick + 프레임 합계 | 0.30 ms (40 ms 예산의 약 0.8%) | 약 1.1 ms |
| 프레임 생산 할당량 | tick당 약 272 KiB (프레임당 약 8.5 KiB) | — |
| 프레임 페이로드 | 평균 1,958 B | — |
| `Checkpoint()` (DB 34 KiB, 방 8개) | 약 1.4–1.8 ms | 최대 약 9–10 ms |

## 해석

- **시뮬레이션과 프레임 생성은 싸다.** 32 스트림 목표에서 합쳐 한 코어의 1% 미만이다. 호스트 비용을 지배할 것은 이 구간이 아니라
  네트워크/TLS 송신, 수신자별 서버 스레드, 그리고 아래 저장 구간으로 보인다(후자는 측정하지 않음).
- **저장은 tick을 막는다.** `Checkpoint()`는 `fsync`를 전역 락 안에서 동기적으로 수행한다. 여기서는 최대 약 10 ms였지만
  이는 SSD에서의 값이다. 느린 디스크(SD 카드, 네트워크 드라이브, 백신 간섭)에서는 `fsync`가 40 ms tick보다 길어져 방 전체가
  그만큼 멈추고 수신자 프레임이 늦게 간다. 개인 호스트(Open, 사용자 PC)에서 특히 가능성이 있다. 이번 PR은 설계를 바꾸지 않았다.
  완화 후보(락 밖에서 직렬화·쓰기, 저장 빈도 조정)는 별도 단계로 판단한다.
- 프레임 생산은 프레임당 약 8.5 KiB를 할당한다(JSON 직렬화). 서버 GC 압력의 대부분이 여기이며, 수신자당 직렬화 결과 재사용 같은
  최적화 여지는 있지만 지금 수치로는 급하지 않다.

## 한계

- **단일 스레드, 소켓 없음**: 실제 서버는 수신자마다 `PeriodicTimer` 송신 작업이 있고 TLS 암호화를 한다. 그 비용은 이 값에 없다.
- 합성 Camp/Field(방당 개체 6개). 몬스터가 많은 큰 월드, 전투·전리품이 많은 방은 비용이 더 든다.
- 분산 측정이 아니다. 한계값은 일부러 넓다(tick+프레임 중앙값 20 ms 미만, 프레임 할당 16 MiB/tick 미만, 8개 방 DB 1 MiB 미만,
  체크포인트 중앙값 1초 미만). 느린 CI 러너에서 흔들리지 않으면서 **알고리즘적 폭증**만 잡는다. 정밀한 SLA가 아니다.
- 디스크 의존 값(체크포인트)은 기기마다 크게 다르다. 로컬 SSD 값을 느린 디스크로 외삽하지 않는다.
