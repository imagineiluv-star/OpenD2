# 아키텍처와 기술 결정

## ADR-001: Godot .NET과 독립 C# 코어

상태: 구현 기준으로 채택, M3 대표 장면에서 품질·성능 재평가.

Godot는 화면·입력·음향·애니메이션·UI를 담당한다. 게임 판정과 저장은 독립 C# 라이브러리에 둔다. Godot의 소스 접근성과 C# 활용을 선택 이유로 삼는다. Unity 기반 Diablerie는 참고 구현으로 사용하며 UnityEngine 의존 타입은 코어로 반입하지 않는다.

Godot 4 계열 안정판 .NET 에디션을 사용한다. 정확한 Godot 버전, Godot.NET.Sdk 및 .NET TFM은 M0에서 실제 Windows/macOS 내보내기에 성공한 조합으로 고정한다. 코어에 최신 .NET을 먼저 강제하여 Godot와 호환되지 않게 만들지 않는다. `global.json`, 프로젝트 SDK 버전, 패키지 잠금 파일, CI 도구 버전을 함께 기록한다.

## 초기 프로젝트 구조

기존 C++ 코드는 비교 기준으로 유지하고 새 코드는 `src/`에 추가한다. 아래는 예정 경로이다.

| 프로젝트/경로 | 책임 | 프로젝트 참조 |
|---|---|---|
| `src/OpenD2.Core` | 게임 상태, 전투, 아이템, 퀘스트, 지역 상태, 저장 DTO와 버전 변환 | 없음 |
| `src/OpenD2.Assets` | MPQ 접근, 포맷 해독, 테이블·콘텐츠 매핑 | Core |
| `src/OpenD2.Client` | Godot 프로젝트, 입력, 2D/3D 표현, UI, 로컬 저장 I/O | Core, Assets |
| `tools/OpenD2.AssetAudit` | 자산 목록·해시·디코딩 결과 점검 CLI | Core, Assets |
| `tests/OpenD2.Tests` | 파서 경계·규칙·저장·콘텐츠 계약 시험 | Core, Assets |

초기부터 Abstractions/Services/Managers 프로젝트를 나누지 않는다. 별도 호스트가 필요해지는 M5에서만 `OpenD2.Server`를 추가한다. 인터페이스는 자산 접근·저장·전송처럼 실제 교체 경계에만 둔다. 게임 내부 객체마다 인터페이스나 DI 등록을 만들지 않는다.

Core와 Assets에는 `Godot`, `UnityEngine`, GPU 텍스처, 장면 노드 참조를 두지 않는다. 디코더는 픽셀·팔레트·프레임 시간·타일 셀·충돌 정보 등 엔진 독립 결과를 반환하고 Client가 이를 Godot 리소스로 변환한다. 좌표 변환은 Client 경계에서 수행한다.

## 시뮬레이션 및 화면 갱신

1. 입력을 명령으로 변환하여 로컬 세션에 전달한다.
2. 단일 시뮬레이션 소유 스레드가 고정 tick으로 명령과 게임 상태를 갱신한다.
3. Client는 상태 스냅샷과 시각 이벤트를 받아 프레임 사이를 보간한다.
4. 피해량·아이템 생성·퀘스트 진행은 화면 노드가 직접 결정하지 않는다.

tick은 호환성 검증 전 잠정 25Hz로 둔다. 실제 프레임 기반 스킬·애니메이션 규칙과 대조한 뒤 확정한다. 렌더링은 60fps 이상을 독립 목표로 삼는다. tick 밀림에는 제한된 따라잡기를 적용하고 초과를 계측한다. 렌더 프레임마다 전체 월드 객체나 DTO를 새로 생성하지 않는다.

난수는 명시적으로 주입하고 시드·필요한 난수 상태를 저장한다. 동일 입력 재생은 테스트 목표이다. .NET 플랫폼 간 비트 단위 결정성은 검증 없이 보장하지 않으며 멀티플레이 lockstep의 전제로 삼지 않는다. 신규 3D 물리 표현이 기존 판정·랜덤 결과를 바꾸지 않도록 한다.

## ADR-002: 로컬 우선, 선택적 협동 세션

싱글플레이는 네트워크와 중앙 서버 없이 완결한다. 협동 모드에서는 한 호스트 또는 전용 서버가 상태를 판정하고 클라이언트는 입력을 보낸다. 호스트가 이동·스킬·획득 명령의 유효성을 검증한다. 원본 패킷 ABI를 유지할 필요는 없다.

향후 전송 규약은 명시적 버전·길이 상한·순번·시간 제한을 포함한다. TCP 사용 시 분할·병합 수신을 처리하고, 스냅샷 전송 시 관심 지역과 변경분을 제한한다. 기존 OpenD2의 패킷 포인터 증가와 수신 버퍼 처리를 그대로 이식하지 않는다.

외부 협동 연결에 필요한 NAT 중계·로비는 별도 비용과 서비스 의존성이 생긴다. P2P/호스트 방식도 연산·대역폭이 0이 아니다. 오프라인 캐릭터와 신뢰 가능한 온라인 경제는 분리해야 하며 초기 단계에서는 온라인 경제를 제공하지 않는다.

### 실제 배치와 서버 구성

| 실행 형태 | 판정 소유자 | 화면·설치 | 현재 상태 |
|---|---|---|---|
| 싱글플레이 | 사용자 PC의 `OpenD2.Core` | `OpenD2.Client` 배포 폴더 하나, 중앙 서버/DB 불필요 | M2 구현 중 |
| 방장 협동 | 방장 PC의 Core, 참가자는 입력 송신/상태 수신 | 방장은 화면과 판정을 함께 실행 | M5 예정 |
| 전용 서버 | `OpenD2.Server` .NET 호스트의 Core | Linux/Windows에서 그래픽 없이 실행, Godot 렌더러 불필요 | M5 예정, 프로젝트/서버 실행 파일 아직 없음 |

서버 호스트는 연결·세션·입력 수신·저장 I/O와 제한된 송수신 큐를 담당하고, Core는 tick별 판정을 담당한다. 서버가 판정한 위치·체력·아이템/퀘스트 변경과 이벤트를 참가자에게 보낸다. 클라이언트가 보낸 체력·피해·드롭 결과를 신뢰하지 않는다. 명령의 ActorId가 실제 연결의 소유 플레이어인지 확인하는 검사는 전송 경계에서 추가해야 한다. 현재 Core의 ID/순번/지역 검사는 네트워크 인증이 아니다.

현재 M2-03 월드는 **플레이어 1명·활성 지역 1개**이며 나머지 지역을 메모리 안에서 정지한다. M5 전에 플레이어별 지역/퀘스트 상태, 여러 플레이어가 머무는 활성 지역 집합, 접속/이탈·관심 영역 동기화·입력 속도 제한·재접속을 구현해야 한다. 같은 Core 규칙을 재사용한다는 뜻이며 현 상태에 소켓만 붙여 멀티플레이가 완성되는 것은 아니다. 대형 월드의 로딩·해제·낮은 빈도 AI는 M6에서 실측한다.

## ADR-003: 원본 표현과 신규 3D 표현의 공존

콘텐츠의 안정적인 ID와 게임 규칙을 표현 데이터와 분리한다. 예를 들어 한 몬스터 정의에는 원본 애니메이션 참조와 선택적 3D 장면 참조를 연결한다. 3D 표현이 없으면 해당 콘텐츠의 원본 표현을 사용할 수 있어야 한다. 혼합 표현의 크기·깊이·가림·그림자·공격 시점을 M3에서 검증한다.

고품질 PC 모드는 Forward+를 기준으로 한다. 저사양 모드의 조명·그림자·이펙트 품질을 별도 구성한다. Compatibility로 전환만 하면 같은 화면이 나온다고 가정하지 않는다. UI는 해상도·DPI·컨트롤러 입력을 고려하고 디자인 토큰과 재사용 장면으로 구성한다.

3D 모델은 Blender/glTF 등에서 제작한다. 원본 스프라이트를 확대하는 것과 리깅된 3D 캐릭터 제작은 다르다. 시각 품질 달성에는 모델·재질·애니메이션·이펙트·사운드 작업과 아트 검수가 필요하다.

## ADR-004: 지역 단위 확장

지역 식별자 `RegionId`, 생성 시드, 콘텐츠 버전, 상태 차이를 저장 모델에 포함한다. 현재 지역과 주변의 제한된 지역만 메모리에 둔다.

지역 수명주기: Unloaded → Loading → Ready → Active → Saving → Unloaded. 실패 시 기존 활성 지역을 유지하고 재시도 가능한 오류를 표시한다. 로딩 요청에는 세대 번호와 취소를 적용하여 이미 떠난 지역의 늦은 결과가 활성화되지 않게 한다.

- 파일 읽기·해독은 제한된 백그라운드 작업으로 실행한다.
- Godot 객체 생성과 GPU 등록은 지원되는 스레드 규칙을 지키고 프레임 예산으로 나눈다.
- 가까운 적은 정상 AI, 먼 활성 지역은 낮은 빈도, 비활성 지역은 저장 상태로 관리한다.
- 에셋 캐시는 바이트 상한과 참조 수명으로 관리한다. 공유 텍스처를 사용 중인 지역보다 먼저 해제하지 않는다.
- 경계 이동은 도착 지역 준비 후 원자적으로 활성 소유권을 넘긴다. 저장 실패 시 원본 상태를 유지한다.

초기에는 고정 시점 액션 RPG를 유지한다. 자유 시점·수직 이동·광대한 연속 지형은 별도 범위이며 원본 등각 타일만으로 완성되지 않는다. 대형 월드의 좌표 정밀도 전략은 M6에서 측정 후 원점 이동 또는 엔진 빌드 옵션을 선택한다.

## 저장 설계

새 저장 포맷에 schemaVersion, contentVersion, 캐릭터, 인벤토리, 퀘스트, 지역 시드·변경분을 기록한다. 임시 파일 작성 → 검증 → 원자 교체와 이전 정상본 백업을 적용한다. 사용자 데이터는 설치 폴더와 분리한다.

원본 `.d2s`는 지원 버전별 가져오기 기능으로 제공하고 원본 파일을 덮어쓰지 않는다. D2R 최신 세이브 지원은 별도 시험 없이 표시하지 않는다. 버전 변환은 이전 fixture로 검증하고, 알 수 없는 새 버전은 명확히 거부한다.

## M2-01 실행 계약 (도입 시 rules v1, 현재 v3)

구현: `GameSimulation`, `FixedTickClock`, `SimulationRandom`과 Client의 `SimulationPreview`. Core는 단일 소유 스레드에서 실행하며 외부 시계·엔진·파일 I/O·이벤트 콜백을 호출하지 않는다. 동시 Submit/Step은 지원하지 않는다. 향후 네트워크 수신은 소유 스레드 큐 앞에서 별도로 정렬·검증해야 한다.

- 기본 25Hz, 정수 시간 누산은 40ms 단위다. 프레임당 최대 5 tick을 실행하고 입력 시간은 250ms로 제한한다. 남은 완전 tick 시간은 버리고 부분 시간은 보간에 남긴다. 버린 벽시계 시간만 계측하며 게임 tick ID를 건너뛰지 않는다. 오프라인 도구 정책이며 네트워크 따라잡기 규약이 아니다.
- 명령은 target Tick, Actor, Region, 단조 증가 Sequence와 값으로 전달한다. 같은 actor의 제출 target tick은 감소할 수 없다. 승인 순서와 적용 순서를 구분하며 적용 순서는 `(Tick, ActorId, Sequence)`다. 거절은 상태·난수·순번을 바꾸지 않는다.
- 전역 entity ID와 region ID를 분리한다. 좌표는 tile당 256 정수 단위, 이동 의도는 각 축 -1/0/1이다. 현재 자유 이동은 축당 32, 대각선당 23단위/tick이며 최종 게임 이동 규칙이 아니다. 판정은 엔진 물리/부동소수점 보간과 독립이다.
- 이벤트는 한 tick의 값 목록이며 callback으로 게임 상태에 재진입하지 않는다. Client가 tick 직후 읽어 처리한다. borrowed state/event span은 다음 Step까지만 사용하고 보관에는 소유 사본 Snapshot을 쓴다. 일반 렌더 프레임은 전체 snapshot을 복제하지 않는다.
- 원본 OpenD2의 uint32 xorshift 전이를 명시적 seed/state로 유지한다. 0 상태는 거절한다. 범위 변환은 16비트 축소 대신 rejection sampling을 사용한다. 원본 Diablo 게임 RNG 호환은 별도 검증한다.
- rules v1의 SHA-256은 little-endian 정수 상태·난수·입력 watermark·정렬된 예약 명령을 포함한다. 이벤트 소비/벽시계/렌더 좌표/성능 지표는 판정 상태에 포함하지 않는다. hash는 명시적 진단 시에만 계산한다.
- 재생은 시작 seed·entity 값과 승인 당시 tick을 포함한 명령 로그에서 새 세션을 만든다. 잘못된 순서·거절 명령·예산 초과는 실패하며 원래 세션을 수정하지 않는다. 저장 포맷/스냅샷 복원/원본 세이브 가져오기는 M2-05다.

상한과 실제 검증 증거, 남은 호환성 범위는 [M2_01_RESULTS](M2_01_RESULTS.md)에 기록한다. rules를 바꾸는 후속 구현은 버전과 golden state 기준을 의도적으로 갱신한다.

## M2-02 충돌·전투 실행 계약 (rules v2)

`CollisionGrid`는 Core의 불변 충돌 데이터다. Assets의 `MapScene.ToCollisionGrid`가 DS1/DT1의 5×5 하위 셀을 변환한다. 이 경계의 256 정수 단위는 탐색 셀 하나이며 DS1 타일 하나는 5셀이다. 모르는 셀과 지도 밖은 통과를 막는다. 런타임은 세션당 한 지역·최대 128개 전투 객체로 제한한다.

tick 순서는 타이머 갱신 → 정렬된 명령 → AI 의도 → ID 순 공격 → ID 순 X/Y 이동 → tick 확정이다. 시작 시 피격 정지 상태였던 객체는 그 tick을 쉬며, 같은 tick에 맞은 객체도 이후 행동을 중단한다. 동일 tick의 우선권은 ID 순서이며 동시 피해 모델이 아니다. 근접 거리·시야·쿨다운 실패는 난수를 소비하지 않는다. 사망한 객체의 예약 명령은 예정 tick에 폐기하고 새로운 명령은 거절한다.

몸체는 반폭 64의 축 정렬 사각형이며 접촉은 허용하고 겹침은 막는다. 축 32/대각선 23의 이동량과 X 후 Y 슬라이딩을 사용한다. 공격은 정수 supercover로 벽·미확인 셀·코너 통과를 차단한다. AI는 6셀 안의 가장 가까운 생존 플레이어를 추적하고 사거리 1.5셀에서 공격한다. 직선 추적이며 경로 탐색은 후속 범위다.

rules v2 해시는 지도 유무·지역·원점·크기·셀, 객체 종류·체력·타이머·AI 상태/대상, 명령 대상을 추가한다. v1 해시와 호환되지 않는다. 초기 상태+동일 불변 지도+seed+입력 로그로 재생한다. 현재 생성자는 새 게임용이며 진행 중 snapshot 복원은 M2-05에서 구현한다. 전투 수치는 독립 최소 규칙으로 원본 Diablo II 밸런스 호환을 뜻하지 않는다. 구현과 검증·상한의 상세는 [M2_02_RESULTS](M2_02_RESULTS.md)를 참조한다.

## M2-03 지역·퀘스트 실행 계약 (rules v3)

`WorldDefinition`은 정렬된 지역별 충돌 지도, 포털의 출발/도착점, 비전투 NPC 하나와 처치 대상 목록을 소유한다. 콘텐츠 SHA-256을 한 번 계산한다. `GameSimulation`이 모든 객체와 퀘스트의 변경 가능한 상태를 소유하며 Client는 기존 명령 경계로 `Interact`를 보낸다. NPC/포털은 체력·몸체가 없는 상호작용 지점이다.

활성 지역만 타이머·AI·전투·이동을 진행한다. 비활성 지역의 객체는 위치·체력·사망·타이머·AI 모드/대상을 유지한다. 전환은 기존 tick의 전투와 이동 이후, 가까운 포털/시야·생존·피격/공격 상태와 목적지 몸체 충돌을 검사한 뒤 적용한다. 목적지 검증 실패 시 전환을 적용하지 않고 출발 지역과 예약 입력을 유지한다. 해당 tick의 정상 전투/타이머까지 되돌리는 전체 tick 롤백은 아니다.

성공 시 플레이어의 지역·위치·활성 충돌 지도를 바꾸고 이동 의도 및 남은 예약 명령을 지운다. 입력 sequence의 최댓값은 보존하되 제출 tick 경계는 전환 tick으로 조정하여 새 지역의 즉시 입력을 허용한다. 들어간 지역의 진행은 다음 tick부터 시작한다. 이 모델은 사전 로드한 메모리 내 전환이며 디스크 저장이나 비동기 스트리밍 실패 처리는 아직 아니다.

퀘스트 상태는 Available → Active → ReadyToTurnIn → Completed다. 수락 전에 처치한 목표도 인정하며 다시 대화하면 완료할 수 있다. 완료 시 체력을 한 번 회복하고 다시 대화해도 보상을 반복하지 않는다. 퀘스트/포털 상호작용은 tick당 마지막 명령 한 번만 실행한다. 동일 tick의 성공한 공격이나 피격/사망은 상호작용을 막는다.

상한: 8지역, 합계 1,048,576셀, 32포털, 32퀘스트 대상, 지역별 주민 127 + 이동 플레이어 1명이다. 전투 갱신은 활성 객체만 수행하나 탐색은 전체 유한 배열을 순회하므로 큰 월드에서는 지역별 인덱스가 필요하다. v3 해시는 전체 객체 상태·활성 지역·퀘스트 상태와 전체 콘텐츠 hash를 포함한다. 자세한 증거와 제한은 [M2_03_RESULTS](M2_03_RESULTS.md)에 기록한다.
